1. CRITICAL BUGS & SECURITY VULNERABILITIES
================================================================================

1.1. Razorpay Amount Tampering & Payment Replay Attack (Critical Financial Bug)
--------------------------------------------------------------------------------
- File Location: backend/controllers/paymentController.js (Lines 250 - 290)
- Issue:
  In `verifyCustomerPayment`, the controller accepts `amount` directly from
  `req.body.amount` and deducts it from the customer ledger balance:
      relation.balance -= Number(amount);
  The Razorpay HMAC signature verification (`razorpay_order_id|razorpay_payment_id`)
  validates only the authenticity of the payment ID against the order ID;
  it DOES NOT validate the amount paid!
- Impact:
  A malicious user can initiate a payment for ₹1, pay ₹1 on Razorpay, and submit
  `amount: 50000` in the payload to wipe out their entire debt.
  Furthermore, `razorpay_payment_id` is NEVER checked for uniqueness or recorded
  in a unique index in the database. The exact same payment ID can be replayed
  repeatedly to decrease the balance to negative infinity.
- Fix Logic:
  1. Fetch payment details from Razorpay API via SDK:
     `const payment = await rzp.payments.fetch(razorpay_payment_id);`
     Verify `payment.status === 'captured'` and `payment.amount === order.amount`.
  2. Add a `unique` constraint on `razorpayPaymentId` in the Payment schema to
     prevent duplicate/replay submissions.

1.2. Permanent Development Authentication Backdoor in Production
--------------------------------------------------------------------------------
- File Location: backend/controllers/authController.js (Lines 161 - 163, 224 - 226)
- Issue:
  The endpoints `verifyOtp` and `registerCustomer` include a bypass:
      if (idToken.startsWith('DEV_TOKEN_')) {
        phone = idToken.replace('DEV_TOKEN_', '');
      }
  This check has NO environment guard (`process.env.NODE_ENV === 'development'`).
- Impact:
  In production, any attacker can send `idToken: "DEV_TOKEN_<target_phone>"` and
  log in as any customer without requiring OTP authentication.
- Fix Logic:
  Enforce strict environment validation:
  `if (process.env.NODE_ENV !== 'production' && idToken.startsWith('DEV_TOKEN_'))`
  or eliminate the bypass completely in release builds.

1.3. IDOR / Cross-Customer Order Injection
--------------------------------------------------------------------------------
- File Location: backend/controllers/orderController.js (Lines 13 - 20)
- Issue:
  In `createOrder`, when `req.user.role === 'customer'`, the controller extracts
  `customerId` from `req.body.customerId` without asserting that
  `req.user._id.toString() === customerId`.
- Impact:
  A logged-in customer can place orders specifying any other customer's ID,
  causing balance deductions and ledger entries on someone else's account.
- Fix Logic:
  For customer role, strictly enforce:
  `const customerId = isVendor ? req.body.customerId : req.user._id;`

1.4. Deadlock on Cross-Role Phone Number Registration
--------------------------------------------------------------------------------
- File Location: backend/controllers/authController.js (Lines 176 - 242)
- Issue:
  In `verifyOtp`, customer lookup filters by `{ phone, role: 'customer' }`.
  If a phone number belongs to an existing `vendor` or `admin`, `verifyOtp` fails
  to find a customer and returns `isNewUser: true`.
  When the user subsequently posts to `registerCustomer`, it checks
  `User.findOne({ phone })` without the role filter, finds the user, and throws
  HTTP 400 "User with this phone already exists".
- Impact:
  The user is trapped: login prompts them to register, but registration always fails.
- Fix Logic:
  Perform lookup on `User.findOne({ phone })` first. If an account with that phone
  already exists under a non-customer role, return an explicit error:
  "This phone number is registered as a business/admin account. Please use the business portal."

1.5. Phone Verification Bypass in Customer Profile
--------------------------------------------------------------------------------
- File Location: backend/controllers/customerController.js (Lines 102 - 113)
- Issue:
  The backend provides OTP-protected endpoints (`requestPhoneChange` and
  `verifyPhoneChange`), yet `updateProfile` (`PUT /api/v1/customer/profile`)
  permits updating `phone` directly without any OTP check.
- Impact:
  Any authenticated customer can circumvent the entire OTP change flow.
- Fix Logic:
  Remove the ability to update `phone` via `updateProfile`. Only permit phone updates
  through `verifyPhoneChange`.

1.6. Unhandled Crash on Missing Firebase Credentials
--------------------------------------------------------------------------------
- File Location: backend/config/firebase.js (Lines 22 - 24)
- Issue:
  `initializeApp({ credential: cert(serviceAccount) })` executes unconditionally
  at module load time. If Firebase environment variables are missing or malformed,
  Node.js throws an unhandled exception and immediately crashes the entire backend.
- Fix Logic:
  Initialize Firebase conditionally or wrap initialization in a safe singleton
  with error trapping and defensive configuration checks.

1.7. Plaintext Secret Storage
--------------------------------------------------------------------------------
- File Location: backend/models/User.js (Lines 45 - 49) & backend/models/RazorpayConfig.js
- Issue:
  `razorpayKeySecret` is stored as plaintext in MongoDB and sent in JSON responses
  to the frontend client in vendor profile routes.
- Fix Logic:
  Encrypt secrets at rest using AES-256-GCM. Never return `razorpayKeySecret` to
  the frontend; instead return boolean `hasSecret: true/false`.

2. BUSINESS LOGIC & DATA INTEGRITY ISSUES
================================================================================

2.1. Missing MongoDB Database Transactions (Risk of Inconsistent State)
--------------------------------------------------------------------------------
- File Location: backend/controllers/orderController.js (Lines 126 - 151, 213 - 249)
- Issue:
  Order placement and status updates execute multiple separate database writes:
  1. `Order.create(...)`
  2. `relation.balance += totalAmount` & `relation.bottlesOutstanding += ...`
  3. `Product.findByIdAndUpdate(..., { $inc: { stock: -quantity } })`
  4. Optional `Payment.create(...)`
- Impact:
  Without MongoDB sessions and transactions, if an operation fails or the server
  restarts midway, the system ends up in a corrupted state (order recorded, but stock
  not deducted, or balance modified without an order).
- Fix Logic:
  Wrap multi-document writes in a MongoDB session transaction:
  `const session = await mongoose.startSession();`
  `await session.withTransaction(async () => { ... });`

2.2. Negative Stock Race Condition
--------------------------------------------------------------------------------
- File Location: backend/controllers/orderController.js (Lines 118 - 123)
- Issue:
  Inventory is checked using an application-level loop (`productInfo.stock < item.quantity`)
  and decremented afterward using `$inc: { stock: -item.quantity }`.
- Impact:
  Two simultaneous orders for the last available unit will both pass the check,
  driving inventory into negative stock.
- Fix Logic:
  Perform atomic conditional decrement:
  `Product.findOneAndUpdate({ _id: id, stock: { $gte: quantity } }, { $inc: { stock: -quantity } }, { session })`

2.3. Broken Order Cancellation (Ghost Debt & Lost Inventory)
--------------------------------------------------------------------------------
- File Location: backend/controllers/orderController.js (Lines 175 - 210)
- Issue:
  If a vendor marks an order as `delivered` and later updates it to `cancelled`,
  `order.status` updates to `cancelled`, BUT `relation.balance`,
  `relation.bottlesOutstanding`, and `Product.stock` are NEVER refunded or reverted.
- Impact:
  The customer remains billed for an order marked as cancelled, bottles are still
  counted as delivered, and stock is lost from inventory.
- Fix Logic:
  When cancelling a previously delivered order, execute reversal logic:
  - `relation.balance -= order.totalAmount`
  - `relation.bottlesOutstanding -= (order.bottlesDelivered - order.bottlesReturned)`
  - `$inc: { stock: +quantity }` on each product.

2.4. Destructive Partial Delivery Logic
--------------------------------------------------------------------------------
- File Location: backend/controllers/orderController.js (Lines 105 - 112)
- Issue:
  When a delivery is partially fulfilled (`finalDelivered < totalQty`), the code
  overwrites `orderProducts[0].quantity = finalDelivered`.
- Impact:
  This destroys historical knowledge of what the customer originally requested.
  Furthermore, because of `if (orderProducts.length === 1)`, orders with 2 or more
  items CANNOT be partially delivered at all and reject with an error.
- Fix Logic:
  Store `requestedQuantity` and `deliveredQuantity` as distinct fields on items,
  and support itemized partial delivery quantities across multiple products.

2.5. Orphaned Payments on Vendor Deletion
--------------------------------------------------------------------------------
- File Location: backend/controllers/adminController.js (Lines 260 - 275)
- Issue:
  `deleteVendor` cascades deletions across Orders, Products, VendorCustomers,
  and VendorSubscriptions, but completely omits `Payment.deleteMany({ vendorId })`.
- Fix Logic:
  Include `await Payment.deleteMany({ vendorId: vendor._id });` in deletion routines.

2.6. Inaccurate Admin Revenue Metric
--------------------------------------------------------------------------------
- File Location: backend/controllers/adminController.js (Lines 182 - 184)
- Issue:
  `totalRevenue` is calculated as the sum of plan prices of currently active
  subscriptions only.
- Impact:
  Expired subscriptions, previous renewals, and historical customer payments are
  ignored, providing an inaccurate financial summary.
- Fix Logic:
  Aggregate total revenue from actual historical payment records or subscription logs.

3. DATABASE & BACKEND PERFORMANCE OPTIMIZATION
================================================================================

3.1. Elimination of N+1 Query in Admin Vendor Directory
--------------------------------------------------------------------------------
- Current:
  `getVendors` retrieves all vendors, then loops through each vendor using
  `Promise.all` to query `VendorSubscription.findOne` and `VendorCustomer.countDocuments`.
  For 100 vendors, this executes 201 individual queries!
- Optimization:
  Use a single MongoDB Aggregation Pipeline:
  `User.aggregate([`
  `  { $match: { role: 'vendor' } },`
  `  { $lookup: { from: 'vendorsubscriptions', ... } },`
  `  { $lookup: { from: 'vendorcustomers', ... } },`
  `  { $project: { ... } }`
  `])`
  This reduces 201 database roundtrips down to 1 single optimized query.

3.2. Elimination of Duplicate Product Lookups
--------------------------------------------------------------------------------
- Current:
  In `createOrder`, products are looked up sequentially via `Product.findById`
  in a loop for price validation, and then queried again inside a second loop for stock.
- Optimization:
  Batch retrieve all products in a single operation:
  `const products = await Product.find({ _id: { $in: productIds } });`
  Map by ID in memory for instant O(1) property lookups.

3.3. Database Indexing Strategy
--------------------------------------------------------------------------------
Add missing compound indexes to `models/`:
- `Order`:
  `orderSchema.index({ vendorId: 1, createdAt: -1 });`
  `orderSchema.index({ customerId: 1, createdAt: -1 });`
  `orderSchema.index({ vendorId: 1, status: 1 });`
- `Payment`:
  `paymentSchema.index({ vendorId: 1, paymentDate: -1 });`
  `paymentSchema.index({ customerId: 1, paymentDate: -1 });`
- `VendorSubscription`:
  `vendorSubscriptionSchema.index({ vendorId: 1, isActive: 1, endDate: 1 });`
- `Product`:
  `productSchema.index({ vendorId: 1, isActive: 1 });`

3.4. Pagination Implementation
--------------------------------------------------------------------------------
- Current:
  `getOrders`, `getPayments`, and `getCustomers` return unbounded arrays.
  In a production water delivery operation with hundreds of daily deliveries,
  this will cause high latency, memory bloat, and server timeouts.
- Optimization:
  Add `page` and `limit` query parameters with sensible defaults (e.g., limit 20)
  using `.skip((page - 1) * limit).limit(limit)`.

3.5. PDF Statement Generation Optimization
--------------------------------------------------------------------------------
- Current:
  `exportPDFReport` generates PDFs using `pdfkit` synchronously on Node.js's
  main event loop thread.
- Optimization:
  Offload CPU-intensive PDF rendering to Node.js Worker Threads (`worker_threads`)
  or stream data in chunks with proper backpressure.

4. FRONTEND ARCHITECTURE & PERFORMANCE OPTIMIZATION
================================================================================

4.1. Monolithic Component Sprawl
--------------------------------------------------------------------------------
- Current State:
  - `VendorDashboard.jsx`: 2,721 lines
  - `AdminDashboard.jsx`: 1,192 lines
  - `CustomerDashboard.jsx`: 1,112 lines
- Problem:
  Every state change (e.g. typing into a modal input or toggling a dropdown)
  triggers a re-render of thousands of JSX DOM nodes.
- Recommended Architecture:
  Decompose into dedicated tab and modal components:
  frontend/src/
    components/
      vendor/
        OverviewTab.jsx
        ProductsTab.jsx
        CustomersTab.jsx
        DeliveriesTab.jsx
        PaymentsTab.jsx
        SettingsTab.jsx
        modals/
          ProductModal.jsx
          CustomerModal.jsx
          DeliveryModal.jsx
          ProcessRequestModal.jsx

4.2. Sequential Network Request Waterfalls
--------------------------------------------------------------------------------
- Current State:
  In `VendorDashboard.jsx`, `fetchData()` performs 6 sequential awaits:
    await authFetch('/vendor/subscription');
    await authFetch('/vendor/products');
    await authFetch('/vendor/customers');
    await authFetch('/orders');
    await authFetch('/orders/payments');
    await authFetch('/vendor/plans');
- Problem:
  Dashboard load time equals the cumulative SUM of all 6 roundtrips.
- Optimization:
  Execute requests concurrently:
  `const [sub, prod, cust, ord, pay, plans] = await Promise.allSettled([...]);`
  This drops load latency to the time of the single slowest endpoint.

4.3. Full Page Reloads on Internal Navigation
--------------------------------------------------------------------------------
- Current State:
  In `Login.jsx` (line 276) and `BusinessLogin.jsx` (line 167), internal links use
  standard `<a href="/business-login">` tags.
- Problem:
  Causes hard browser reloads, unmounting the React app, resetting state, and
  re-downloading JavaScript bundles.
- Optimization:
  Replace with React Router's `<Link to="/business-login">`.

4.4. Redundant Script Injection
--------------------------------------------------------------------------------
- Current State:
  `loadRazorpayScript` repeatedly appends `<script>` tags to `document.body`
  every time checkout is initiated.
- Optimization:
  Verify `if (window.Razorpay) return true;` before creating or appending scripts.

4.5. State Management & Caching
--------------------------------------------------------------------------------
- Recommendation:
  Integrate TanStack Query (React Query) or SWR for declarative data fetching,
  automatic caching, background revalidation, and optimistic UI updates.

2. Batch product queries in `orderController.js`.
3. Add compound database indexes on Orders, Payments, and Subscriptions.
4. Add pagination to all order, payment, and customer endpoints.

1. Break down 2,700-line `VendorDashboard.jsx` into modular components.
2. Parallelize network requests using `Promise.allSettled`.
3. Replace `<a>` tags with React Router `<Link>`.
