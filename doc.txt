1. SYSTEM OVERVIEW & TECHNOLOGY STACK
================================================================================

1.1. Executive Summary
--------------------------------------------------------------------------------
The Water Supply Management System is a commercial SaaS and logistics platform
engineered for packaged water distributors (20-litre cans, cartons, dispensers).
It solves core industry pain points:
- Recurring delivery scheduling and delivery-slot management.
- Double-ledger accounting: Outstanding monetary balance (INR) AND outstanding
  physical assets (reusable polycarbonate water jars).
- Multi-tier SaaS subscriptions for water distributors with customer limits.
- Field operations: Real-time run-sheets for delivery drivers, self-claiming
  routes, in-field cash collection, and end-of-day warehouse reconciliations.
- Direct-to-distributor online payments via Razorpay integration.

1.2. Technology Stack
--------------------------------------------------------------------------------
BACKEND:
- Runtime: Node.js (v18+ recommended, v24 supported)
- Web Framework: Express.js (v4.19+)
- Database: MongoDB (v5.0+ or v6.0+ with Replica Set for ACID transactions)
- ODM: Mongoose (v8.4+)
- Authentication: JSON Web Tokens (jsonwebtoken v9.0), bcryptjs (v2.4)
- Phone Verification: Firebase Admin SDK (v14.0)
- Payment Gateway: Razorpay Node SDK (v2.9)
- Document Generation: PDFKit (v0.15) for streaming financial statements
- Email Engine: Nodemailer (v9.0) for password reset tokens
- Cryptography: Node.js native `crypto` module (AES-256-GCM authenticated cipher)

FRONTEND:
- Core: React 19 (v19.2+) with JSX
- Build Tool & Bundler: Vite (v8.0+)
- Styling: Tailwind CSS (v4.3+) with @tailwindcss/postcss
- Routing: React Router DOM (v7.17+) with role-based private guards
- Icons: Lucide React (v1.18+)
- Client SDKs: Firebase Web Client SDK (v12.14) for recaptcha & SMS OTP

1.3. User Persona & Role Matrix
--------------------------------------------------------------------------------
The system defines 4 distinct roles enforced via JWT role claims and middleware:

+----------------+-------------------------------------------------------------+
| Role           | Scope & Responsibilities                                    |
+----------------+-------------------------------------------------------------+
| admin          | Platform Owner. Manages subscription plans, views aggregate |
|                | platform revenue, activates/deactivates vendors, manages    |
|                | platform Razorpay gateway keys.                             |
| vendor         | Water Distributor / Business Owner. Manages bottle catalog, |
|                | customer directory, ledger adjustments, delivery staff,     |
|                | shift reconciliations, delivery slots, and own Razorpay key.|
| agent          | Field Delivery Agent / Driver. Mobile-first dashboard to   |
|                | view open deliveries, self-claim orders, record bottles     |
|                | delivered/returned, collect cash on delivery.               |
| customer       | Consumer / Household / Office. Orders water, tracks delivery|
|                | status, selects delivery slots, manages up to 5 addresses,  |
|                | views bottle ledger, and pays outstanding balance online.   |
+----------------+-------------------------------------------------------------+

--------------------------------------------------------------------------------

4. DATABASE ARCHITECTURE & DATA MODELS (MONGOOSE)
================================================================================

4.1. User Schema (`backend/models/User.js`)
--------------------------------------------------------------------------------
Primary identity collection for all 4 roles.
Key Fields:
- `name` (String, required): Full name or company name.
- `phone` (String, required, unique, 10-digits): Primary mobile identifier.
- `email` (String, unique, sparse): Used for business login and password reset.
- `password` (String): Bcrpyt hash (salt rounds: 10, pre-save hook).
- `role` (String, enum: ['admin', 'vendor', 'customer', 'agent'], default: 'customer').
- `vendorId` (ObjectId, ref: 'User'): Required ONLY if role is 'agent'. Links the
  delivery staff member to their employing vendor.
- `address` (String): Primary/default address.
- `addresses` (Array of Strings): Up to 5 saved customer addresses.
- `razorpayKeyId` (String): Vendor's public Razorpay API key.
- `razorpayKeySecret` (String, select: false): Vendor's secret API key.
  Equipped with transparent getters/setters implementing AES-256-GCM authenticated
  encryption via `secretEncryption.js`. Never exposed in JSON serialization.
- `deliverySlots` (Array of Strings): Vendor delivery timing windows.
- `isActive` (Boolean, default: true): Deactivated users are blocked by auth middleware.
- `resetPasswordToken` & `resetPasswordExpire`: SHA-256 token storage for password reset.

4.2. Order Schema (`backend/models/Order.js`)
--------------------------------------------------------------------------------
Represents delivery requests and logged deliveries.
Key Fields:
- `vendorId` (ObjectId, ref: 'User', required, indexed): Distributor fulfilling the order.
- `customerId` (ObjectId, ref: 'User', required, indexed): Recipient customer.
- `deliveryAgentId` (ObjectId, ref: 'User', default: null, indexed): Assigned delivery driver.
- `jarSettlementId` (ObjectId, ref: 'AgentJarSettlement', default: null): Links order to
  the warehouse shift settlement once empty jars are physically handed over.
- `products` (Array of Subdocuments):
  - `productId` (ObjectId, ref: 'Product')
  - `name` (String)
  - `quantity` (Number, legacy/active delivery count)
  - `requestedQuantity` (Number, tracks original customer demand)
  - `deliveredQuantity` (Number, tracks quantity fulfilled)
  - `price` (Number, captured at order time)
- `totalAmount` (Number, required, min: 0): Order subtotal in INR.
- `bottlesDelivered` (Number, default: 0): Total cans handed to customer.
- `bottlesReturned` (Number, default: 0): Empty cans taken back from customer.
- `status` (String, enum: ['pending', 'delivered', 'cancelled'], default: 'pending').
- `deliverySlot` (String): Target time window.
- `deliveryAddress` (String): Physical address for delivery.
- `deliveryDate` (Date): Timestamp when marked delivered.
Compound Indexes:
- `{ vendorId: 1, createdAt: -1 }`
- `{ customerId: 1, createdAt: -1 }`
- `{ vendorId: 1, status: 1 }`
- `{ deliveryAgentId: 1, status: 1, createdAt: -1 }`

4.3. Payment Schema (`backend/models/Payment.js`)
--------------------------------------------------------------------------------
Financial transactions and audit logs.
Key Fields:
- `vendorId` (ObjectId, ref: 'User', required, indexed)
- `customerId` (ObjectId, ref: 'User', required, indexed)
- `orderId` (ObjectId, ref: 'Order', default: null)
- `collectedByAgentId` (ObjectId, ref: 'User', default: null, indexed): Delivery agent
  who physically received cash from customer.
- `agentSettlementId` (ObjectId, ref: 'AgentSettlement', default: null, indexed):
  Set when the delivery agent submits cash to the vendor at shift end.
- `amount` (Number, required, min: 0): Transaction amount in INR.
- `paymentMethod` (String, enum: ['cash', 'online', 'other'], default: 'cash').
- `status` (String, enum: ['pending', 'captured'], default: 'captured').
- `razorpayOrderId` (String, sparse, unique): Idempotency key for online order.
- `razorpayPaymentId` (String, sparse, unique): Idempotency key for gateway payment.
- `notes` (String)
Compound Indexes:
- `{ vendorId: 1, paymentDate: -1 }`
- `{ customerId: 1, paymentDate: -1 }`
- `{ vendorId: 1, collectedByAgentId: 1, agentSettlementId: 1, paymentDate: -1 }`

4.4. VendorCustomer Schema (`backend/models/VendorCustomer.js`)
--------------------------------------------------------------------------------
Maintains the two-sided ongoing commercial relationship:
- `vendorId` (ObjectId, ref: 'User', required)
- `customerId` (ObjectId, ref: 'User', required)
- `balance` (Number, default: 0):
  Positive = Customer owes vendor money (Debt).
  Negative = Customer has an advance balance / credit.
- `bottlesOutstanding` (Number, default: 0):
  Net physical jars held by customer: `(Total Delivered - Total Returned)`.
Compound Index:
- `{ vendorId: 1, customerId: 1 }` (unique)

4.5. AgentSettlement Schema (`backend/models/AgentSettlement.js`)
--------------------------------------------------------------------------------
Reconciliation record for in-field cash handover:
- `vendorId` (ObjectId, ref: 'User', required)
- `agentId` (ObjectId, ref: 'User', required)
- `paymentIds` (Array of ObjectId, ref: 'Payment'): Specific payment records cleared.
- `amount` (Number, required, min: 0.01): Total physical cash received.
- `submittedAt` (Date, default: Date.now)

4.6. AgentJarSettlement Schema (`backend/models/AgentJarSettlement.js`)
--------------------------------------------------------------------------------
Reconciliation record for returned empty jars:
- `vendorId` (ObjectId, ref: 'User', required)
- `agentId` (ObjectId, ref: 'User', required)
- `orderIds` (Array of ObjectId, ref: 'Order'): Deliveries whose returns are cleared.
- `jarCount` (Number, required, min: 1): Total physical empty jars returned to warehouse.
- `submittedAt` (Date, default: Date.now)

4.7. SubscriptionPlan & VendorSubscription
--------------------------------------------------------------------------------
- `SubscriptionPlan`: Tiers with `name`, `price`, `duration` ('monthly', 'quarterly',
  'yearly'), `userLimit` (max customers allowed), and `isActive`.
- `VendorSubscription`: Tracks active tenure for a vendor with `vendorId`, `planId`,
  `startDate`, `endDate`, and `isActive`. Enforced by `checkSubscription` middleware.

4.8. Product Schema (`backend/models/Product.js`)
--------------------------------------------------------------------------------
Distributor catalog items:
- `vendorId` (ObjectId, ref: 'User', required)
- `name` (String, required), `price` (Number, required), `stock` (Number, default: 0),
  `quantity` (String, e.g. "20 Litres"), `imageUrl` (String), `isActive` (Boolean).

5. CORE BUSINESS WORKFLOWS & STATE MACHINES
================================================================================

5.1. Order Lifecycle & Fulfillment
--------------------------------------------------------------------------------
```
[Customer Places Order] ───> Status: PENDING (unassigned)
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
       [Vendor Assigns to Agent]       [Agent Self-Claims Order]
                    │                             │
                    └──────────────┬──────────────┘
                                   │
                                   ▼
                       Status: PENDING (claimed)
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
         [Delivery Agent Delivers]       [Order Cancelled]
                    │                             │
                    ▼                             ▼
         Status: DELIVERED               Status: CANCELLED
         - Deducts product stock         - Reverts balance & jars
         - Updates customer balance        (if previously delivered)
         - Updates jar ledger
         - If Cash: marks Payment
           with collectedByAgentId
```

5.2. Double-Ledger Accounting Mechanics
--------------------------------------------------------------------------------
Whenever an order transitions to `delivered`:
1. Monetary Ledger:
   `VendorCustomer.balance += order.totalAmount`
   If the customer pays cash on delivery:
   `Payment.create({ amount: cashAmount, paymentMethod: 'cash', ... })`
   `VendorCustomer.balance -= cashAmount`
2. Physical Asset (Jar) Ledger:
   `VendorCustomer.bottlesOutstanding += (bottlesDelivered - bottlesReturned)`
   Example: If 2 full cans delivered and 1 empty can returned, `bottlesOutstanding`
   increases by +1. If 0 cans delivered and 2 empty cans returned, it decreases by -2.

5.3. Two-Stage Chain of Custody (Cash & Jars)
--------------------------------------------------------------------------------
Stage 1: In the Field (Customer &rarr; Delivery Agent)
- Delivery agent completes delivery and collects ₹160 cash + 2 empty jars.
- Customer debt is immediately cleared.
- System sets `payment.collectedByAgentId = agent._id` and `agentSettlementId = null`.
- System records `order.bottlesReturned = 2` and `jarSettlementId = null`.
- Result: The cash and empty jars are officially in the AGENT'S physical custody.

Stage 2: At Warehouse (Delivery Agent &rarr; Vendor)
- In the evening, the agent returns to the plant and hands over physical cash and jars.
- Vendor reviews pending sums and clicks "Submit Cash Settlement" / "Submit Jar Settlement".
- An ACID transaction runs:
  - Creates `AgentSettlement` (or `AgentJarSettlement`).
  - Sets `agentSettlementId` on all un-settled Payment documents.
  - Sets `jarSettlementId` on all un-settled Order documents.
- Result: Agent's pending holding resets to 0. Vendor books reflect reconciled cash.

5.4. Customer Phone Authentication Lifecycle
--------------------------------------------------------------------------------
1. Client enters 10-digit mobile number on `/login`.
2. Firebase reCAPTCHA generates SMS OTP.
3. User enters 6-digit OTP &rarr; Firebase Client SDK produces `idToken`.
4. Client calls `POST /api/v1/auth/verify-otp` with `idToken`.
5. Backend verifies token via Firebase Admin SDK and checks MongoDB:
   - If User exists with `role: 'customer'`: returns JWT token and customer profile.
   - If User exists with `role: 'agent'`: returns JWT token, agent profile, vendorId.
   - If User is new: returns `isNewUser: true`. Frontend prompts Name and Address,
     then calls `POST /api/v1/auth/register-customer`.

7. SECURITY, CRYPTOGRAPHY & DATA INTEGRITY
================================================================================

7.1. Symmetric Encryption for Third-Party Secrets (AES-256-GCM)
--------------------------------------------------------------------------------
Vendor `razorpayKeySecret` values are encrypted before writing to MongoDB.
Implementation: `backend/utils/secretEncryption.js`
- Algorithm: `aes-256-gcm` authenticated symmetric encryption.
- Key: 256-bit (32 bytes) hex-encoded key from `RAZORPAY_SECRET_ENCRYPTION_KEY`.
- Format: `enc:v1:<iv_hex>:<auth_tag_hex>:<ciphertext_hex>`.
- Integrity: GCM mode produces an authentication tag preventing ciphertext tampering.
- Data Leak Prevention: Mongoose Schema transforms delete `razorpayKeySecret` during
  JSON serialization and defaults to `select: false`.

7.2. Multi-Document ACID Transactions
--------------------------------------------------------------------------------
All multi-table operations (such as order delivery, inventory deduction, and shift
settlements) are wrapped in MongoDB transactions:
```javascript
const session = await mongoose.startSession();
await session.withTransaction(async () => {
  // 1. Verify and decrement stock atomically
  // 2. Update Order status and delivery timestamp
  // 3. Mutate VendorCustomer ledger balance and bottle count
  // 4. Create Payment log if cash was collected
});
await session.endSession();
```

7.3. Idempotency & Payment Replay Protection
--------------------------------------------------------------------------------
- In `Payment.js`, `razorpayOrderId` and `razorpayPaymentId` have `{ sparse: true, unique: true }`
  indexes. Any duplicate webhook or replayed verification request is rejected
  by MongoDB unique constraint error (E11000).
- Payment verification validates order status and amount before balance deductions.

7.4. Indian Calendar Day Timezone Alignment
--------------------------------------------------------------------------------
Delivery summaries, daily cash collections, and agent statistics are calculated
according to Indian Standard Time (IST / Asia/Kolkata), independently of the
server host's local clock (e.g., UTC on AWS/Heroku/DigitalOcean).
Implementation: `backend/utils/indiaDate.js` generates precise `start` (00:00:00+05:30)
and `end` (24:00:00+05:30) Date boundaries using `Intl.DateTimeFormat`.

10.2. Common Troubleshooting Scenarios
--------------------------------------------------------------------------------
Issue: "Transaction numbers are only allowed on a replica set member or mongos"
Cause: MongoDB is running as a standalone node. MongoDB multi-document transactions
       require a replica set.
Fix: Start mongod with `--replSet rs0` and run `rs.initiate()` in mongosh.

Issue: "RAZORPAY_SECRET_ENCRYPTION_KEY must be configured as 64 hexadecimal characters"
Cause: Missing or invalid key length in `.env`.
Fix: Generate a valid key: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.

Issue: Firebase Auth Error: "auth/invalid-app-credential"
Cause: Domain not whitelisted in Firebase Console.
Fix: Add `localhost` and your production domain under Firebase Console ->
     Authentication -> Settings -> Authorized Domains.

Issue: Delivery Agent cannot log in with OTP
Cause: The agent's phone number was registered under a vendor or customer role previously.
Fix: Phone numbers must be unique across the platform. Verify role in `users` collection.
